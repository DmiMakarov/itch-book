# Неделя 1: заметки

## Почему `mmap`, а не `read()` в буфер

**Разбор становится проще.** С `mmap` весь файл — один непрерывный `std::span<const std::byte>`.
При чтении блоками запись (12–50 байт) может начаться в конце одного блока и закончиться в начале
следующего; нужна логика «перенести хвост в начало буфера и дочитать» — частый источник редких багов.

**Нет копирования.** `read()` копирует данные из page cache в пользовательский буфер; при `mmap`
процесс читает страницы page cache напрямую. Нет и системного вызова на каждый блок.

**Задел на неделю 3.** Zero-copy разбор полей требует, чтобы байты уже лежали непрерывно в памяти.

**Минусы:**
- ошибки ввода-вывода и обрезанный во время работы файл приходят сигналом `SIGBUS`, а не кодом возврата;
- каждый первый доступ к странице — page fault (см. ниже), у `read()` большими блоками переходов
  в ядро меньше; на последовательном чтении `read()` с буфером 1–4 МБ часто не медленнее;
- работает только с файлами: pipe, сокет, `.gz` не отобразить;
- что держать в памяти, решает ядро, а не программа.

Поэтому разборщик принимает `std::span`, а не `MappedFile`: источник байт можно заменить (буфер
`read()`, сетевой пакет MoldUDP64), не трогая разбор.

## Page fault

`mmap` только резервирует диапазон виртуальных адресов. Записи в таблице страниц появляются лениво:
первое обращение к адресу без отображения — исключение процессора, ядро находит нужную страницу
файла и отображает её.

- **Minor fault** — страница уже в page cache, ядро только добавляет запись в таблицу страниц.
- **Major fault** — страницы нет в памяти, ядро читает её с диска, поток ждёт.

**Сколько их на этот файл.** 8 251 407 909 байт / 4096 = **2 014 504 страницы** — столько fault'ов
было бы при отображении по одной странице. Измерено (`/usr/bin/time`, см. README):

| Прогон | Minor | Major | Объяснение |
|---|---:|---:|---|
| Тёплый | ≈ 126 160 | 0 | 2 014 504 / 16 = 125 906: fault-around отображает 64 КБ (16 страниц) за один fault |
| Холодный | ≈ 126 160 | ≈ 62 970 | 2 014 504 / 32 = 62 953: readahead читает с диска 128 КБ (32 страницы) за раз (`read_ahead_kb = 128`) |

То есть ядро само группирует страницы, и fault'ов в 16 раз меньше, чем страниц. Следующие шаги,
чтобы их ещё уменьшить: `MAP_POPULATE`, большие страницы (2 МБ), `madvise(MADV_WILLNEED)`.

## Холодный и тёплый прогон

- **Холодный:** файла нет в page cache, страницы читаются с диска. 10 с, 38 нс/сообщение, 0.8 ГБ/с —
  время определяет диск (виртуальный диск WSL2), а не код.
- **Тёплый:** файл целиком в page cache. 1.8 с, 6.8 нс/сообщение, 4.5 ГБ/с — время определяют
  процессор и память, то есть сам код.

**Какой показывать.** Оба, с явной подписью и методикой. Для сравнения версий кода («было/стало») —
тёплый: он меряет код, а не диск, и стабилен (разброс < 1 %). Холодный отвечает на другой вопрос —
сколько займёт обработка файла с диска целиком — и сильно зависит от машины. В боевой системе данные
приходят из сети в память, так что для разборщика ближе тёплый прогон.

Ловушка: тёплый прогон возможен, только если файл помещается в свободную память. Сейчас доступно
≈ 9.4 ГиБ при файле 7.7 ГиБ; при нехватке памяти начало файла вытесняется к концу прохода и
«тёплый» прогон частично становится холодным.

## `MADV_SEQUENTIAL`

Эффекта нет в пределах шума: тёплый 6.81 против 6.75 нс/сообщение, холодный — медианы 10.2 и 9.9 с
при разбросе ±10 %, число major fault'ов одинаковое. Ядро и без подсказки распознаёт
последовательный доступ и включает readahead; подсказка могла бы помочь при нехватке памяти
(агрессивнее выбрасывать пройденные страницы), но здесь файл помещается в кэш.
