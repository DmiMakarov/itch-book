# Бенчмарки itch-book

Здесь лежит baseline производительности парсера: с ним сравнивается каждая следующая оптимизация.
Правило: одна правка — один прогон против baseline. Если улучшение меньше cv, его нет.

---

## Baseline v1 — 18.11.2026

**Коммит:** `<вписать после коммита>` (поверх `0124dac`)

**Сырые логи:** `docs/bench/` (`bench_tmp.log` — все бенчмарки ×20, `perf_stat.log`, `perf_record.log`, `perf_report.log`)

### Что меряем

`bench/itch/bench_parse.cpp`. Данные — первые 256 МиБ файла `12302019.NASDAQ_ITCH50` (~7.85 млн сообщений),
обрезанные по границе записи и скопированные в `std::vector` **до** замера: page cache и page fault в цифры не попадают,
меряется чистый CPU-разбор. Все три режима идут через один и тот же цикл `itch::handler::consume`.

| Бенчмарк | Что делает |
|---|---|
| `BM_DispatchFrame` | только `ItchReader::next()` — фрейминг, проверка типа/длины/монотонности timestamp |
| `BM_DispatchSys` | `dispatch` с обработчиком только на System Event: остальные 22 типа пропускаются без разбора |
| `BM_DispatchAll` | `dispatch` с разбором и валидацией всех 23 типов |

Распределение типов в файле (всего 268 744 780 сообщений): Add Order 43.6 %, Order Delete 42.6 %,
Order Replace 8.1 %, Order Executed 2.1 %, NOII 1.5 %, остальное < 1.1 % каждое.

### Результаты

Медиана из 20 повторов (`--benchmark_repetitions=20`).
Метрики на сообщение из `perf stat` — оценка: сообщения посчитаны как скорость × user time, туда входит и загрузка `sample()`.

| | нс/сообщ. | млн сообщ./с | ГиБ/с | такты/сообщ. | инстр./сообщ. | IPC | branch-miss/сообщ. | cv |
|---|---|---|---|---|---|---|---|---|
| Frame | **4.2** | 236.5 | 7.54 | ~20 | ~77 | 3.97 | ≈0 | 3.7 % |
| Sys | **5.9** | 171.0 | 5.45 | ~28 | ~108 | 3.88 | ≈0 | 4.7 % |
| All | **12.2** | 81.8 | 2.61 | ~57 | ~163 | 2.87 | 0.35 | 3.1 % |

Разложение по слоям:

- `dispatch` с пропуском (Sys − Frame): ~1.6 нс, ~8 тактов;
- разбор и валидация полей (All − Sys): ~6.4 нс, ~29 тактов, из них ~6 тактов — промахи предсказания `switch` по типу.

Профиль `BM_DispatchAll` (`perf record`, плоский):

| % | Функция |
|---|---|
| 36.0 | `itch::ItchReader::next()` |
| 35.4 | `itch::dispatch<AllHandler>` (с заинлайненными `read_*` большинства типов) |
| 11.8 | `itch::msg::read_add_order_msg` — не заинлайнен |
| 8.0 | `BM_DispatchAll` (цикл `consume` + счётчик по типам) |
| 4.1 | `itch::msg::read_header` `[clone .isra.0]` — не заинлайнен |
| 1.9 | `itch::msg::read_noii_msg` |
| 1.6 | `memmove` (загрузка `sample()`) |

Вспомогательные замеры (`bench_endian.cpp`, `bench_mapped_file.cpp`), медианы:

| | |
|---|---|
| `be16` / `be32` / `be64` | 0.43 / 0.44 / 0.48 нс |
| `be48` | **1.00 нс** — вдвое медленнее `be64` |
| `MapUnmap` 4 КиБ … 64 МиБ | ~4.8–5.3 мкс, от размера почти не зависит (отображение ленивое) |
| `MapAndScan` 64 МиБ, Normal / Sequential | 2.48 / 2.48 ГиБ/с — на горячем page cache `MADV_SEQUENTIAL` ничего не меняет |

Полный файл через `main` (8.25 ГБ, не помещается в page cache): 39–44 нс/сообщ. на «тёплом» прогоне, до 84–140 нс на холодном.

### Выводы

1. **Frame и Sys упираются в CPU, а не в память.** IPC ~4 — около предела ядра, промахов кэша < 0.5 %,
   промахов ветвлений нет. Ускорить можно только сократив число инструкций, а ~77 инструкций на один фрейминг — много.
2. **В All около 10 % времени уходит на непредсказуемый `switch` по типу** (0.35 промаха на сообщение × ~17 тактов ≈ 6 из ~57 тактов).
   Это свойство данных (типы перемешаны), на одном потоке почти не устраняется.
3. **Треть времени All — в `next()`, и это отдельный вызов.** Функция определена в `.cpp` и не инлайнится в цикл:
   каждое сообщение — call/ret и `std::optional<Message>` через память.
4. **Timestamp читается дважды** (в `next()` и в `read_header`), и оба раза через медленный `be48`.
5. **`read_add_order_msg` не инлайнится,** хотя Add Order — самый частый тип (43.6 %).
6. **При работе с файлом узкое место — I/O, а не парсер.** В памяти день разбирается за ~3.3 с CPU, с диска — 11–27 с.
   Оптимизация разбора нужна ради задержки на сообщение (live-фид), а не ради времени обработки файла.

### Кандидаты на оптимизацию

Каждый пункт — отдельный прогон против этого baseline.

- [ ] Сделать `ItchReader::next()` инлайнабельным (перенести в заголовок) или включить LTO.
- [ ] Не читать timestamp повторно: брать `Message::timestamp` в `read_header` или не разбирать его в `next()`.
- [ ] Быстрый `be48`: например, `be16 << 32 | be32` — две загрузки вместо шести.
- [ ] Посмотреть `perf annotate` для `dispatch`: во что превратился `switch` в Sys (одно сравнение?) и в All (jump table?).
- [ ] Проверить влияние `-march=native` и `-O3`.

### Ограничения замера

- WSL2: фоновая нагрузка хоста, cv 3–5 %. Разницу меньше ~5 % этот замер не различает.
- В `BM_DispatchAll` в `DoNotOptimize` уходит только checksum по `header.timestamp`: компилятор вправе
  не вычислять поля, которые в него не попадают (валидацию enum'ов выкинуть нельзя — она бросает).
  Цифра All может быть занижена; проверить через вариант с `DoNotOptimize(msg)` на каждую структуру.
- Нет frame pointer — стеки в `perf record -g` нечитаемы, профиль только плоский.

### Как воспроизвести

```bash
cmake --build --preset release

# бенчмарки
./build/release/bench --benchmark_filter=BM_Dispatch \
    --benchmark_repetitions=20 --benchmark_report_aggregates_only=true

# счётчики
PERF=/usr/lib/linux-tools/6.8.0-149-generic/perf
$PERF stat -e cycles,instructions,branches,branch-misses,cache-references,cache-misses,page-faults \
    -- ./build/release/bench --benchmark_filter=BM_DispatchAll --benchmark_min_time=2s

# профиль
$PERF record -- ./build/release/bench --benchmark_filter=BM_DispatchAll --benchmark_min_time=2s
$PERF report --stdio --no-children

# полный файл
./build/release/main --file=data/12302019.NASDAQ_ITCH50 --handler=all
```
